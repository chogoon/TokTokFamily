# 개발 파이프라인: 구현 → 리뷰 → 테스트

이 스킬은 기능 구현 요청을 받으면 아래 3단계를 **자동으로 순차 진행**하는 고정 절차다. 각 단계는 전담 에이전트에게 위임하고, 실패하면 자동으로 재시도한다.

## 파이프라인

```
1. 구현   → frontend-dev 또는 backend-dev (.claude/agents/)
2. 리뷰   → project-reviewer (.claude/agents/project-reviewer.md)
3. 테스트 → test-runner (.claude/agents/test-runner.md)
```

## 절차

### 0. 범위 판단

요청이 frontend/backend 중 어디에 속하는지 판단한다. 양쪽 다 걸치면(예: 새 테이블 + 화면) backend-dev를 먼저, frontend-dev를 그다음에 순서대로 호출한다.

### 1. 구현 단계

해당 workspace의 전담 에이전트(`frontend-dev` 또는 `backend-dev`)에게 위임한다. 프롬프트에는:
- 구현할 기능과 수용 기준
- 관련 기존 파일 경로
- TDD 요구 (테스트를 먼저 쓰고 구현)
- "작업 후 해당 workspace의 lint/build/test를 직접 실행해 통과를 확인할 것"

구현 에이전트가 자체 lint/build/test를 통과시키지 못하면 이 단계에서 바로 재시도(최대 3회, 아래 "재시도 규칙" 참조)한다.

### 2. 리뷰 단계

구현이 끝나면 `project-reviewer` 에이전트를 호출한다 (`project-review` 스킬과 동일한 위임 방식). CRITICAL 규칙 / RLS·권한 / 아키텍처 준수 / 테스트 존재 / 빌드 가능 체크리스트 결과표를 받는다.

- 모두 ✅면 3단계로 진행.
- ❌가 있으면 해당 항목과 구체적 수정 방안을 그대로 1단계 에이전트(frontend-dev/backend-dev)에게 돌려보내 수정을 요청한다. "재시도 규칙" 적용.

### 3. 테스트 단계

리뷰 통과 후 `test-runner` 에이전트를 호출한다 (`.claude/agents/test-runner.md`). 로컬 스택을 실제로 띄워 정상 경로/경계 조건/RLS 격리를 curl+DB 쿼리로 검증한 결과표를 받는다.

- PASS면 파이프라인 완료. 사용자에게 구현 요약 + 리뷰 결과 + 테스트 결과를 전달하고, 커밋/푸시는 `commit-and-push` 스킬이 담당하므로 원하면 이어서 호출한다.
- FAIL이면 test-runner가 지목한 workspace의 에이전트에게 실패 시나리오를 그대로 전달해 수정을 요청한다. "재시도 규칙" 적용.

## 재시도 규칙

- 리뷰 또는 테스트 단계에서 문제가 발견되면, 구체적인 실패 내용(체크리스트 항목, 시나리오, 에러)을 그대로 해당 구현 에이전트에게 전달해 수정하게 한다.
- 수정 후 다시 같은 단계(리뷰 또는 테스트)부터 재검증한다. 이 사이클을 **같은 이슈에 대해 최대 3회**까지 반복한다.
- 3회 모두 실패하면 자동 재시도를 멈추고, 지금까지의 시도 내역(무엇을 고쳤고 왜 여전히 실패하는지)을 사용자에게 보고하고 지시를 기다린다. 4회차를 임의로 더 시도하지 않는다.
- 매 재시도 라운드가 끝날 때마다 간단히 몇 번째 시도인지 사용자에게 알린다 (예: "리뷰 2차 재시도 중").

## 주의

- 이 스킬은 git 작업을 하지 않는다. 파이프라인이 PASS로 끝난 뒤 커밋/푸시가 필요하면 `commit-and-push` 스킬을 별도로 호출한다.
- test-runner가 데이터 정리를 위해 `npx supabase db reset`을 실행하려 하면, 사용자가 동시에 로컬에서 테스트 중일 수 있으므로 명시적 승인 없이는 실행하지 않도록 한다(`.claude/agents/test-runner.md`에도 이 규칙이 있다).
