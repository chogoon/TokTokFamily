# Architecture Decision Records

## 철학

가족이 아닌 사람은 들어올 수 없는 닫힌 공간, 형제 비교 없음을 최우선 가치로 둔다. 기능을 추가할 때마다 "이게 닫힌 가족 공간 원칙을 깨는가?", "형제를 비교하게 만드는가?"를 먼저 확인한다. MVP 범위를 벗어나는 기능(사진, 음성, 위치 등)은 1차 출시에서 보류한다.

---

### ADR-001: React Native + Expo 선택

**결정**: 앱 프레임워크로 React Native + Expo를 사용한다.
**이유**: iOS와 Android를 하나의 코드베이스로 만들 수 있고, 기존 웹 프로토타입(`family-sns.html`)의 HTML/JS 구조를 컴포넌트로 옮기기 쉽다.
**트레이드오프**: Flutter 대비 네이티브 성능 최적화 여지가 적을 수 있으나, 초기 개발 속도와 생태계(Expo Notifications 등)를 우선한다.

### ADR-002: Supabase를 서버/DB로 선택

**결정**: 백엔드로 Supabase(Auth, Postgres, Realtime, Storage)를 사용한다.
**이유**: 가족-구성원-방-권한처럼 서로 연결된 관계형 데이터가 많아 Postgres 기반이 적합하고, RLS(행 단위 보안)로 "우리 가족 데이터만 보기"를 DB 레벨에서 강제할 수 있다.
**트레이드오프**: Firebase(Firestore)보다 러닝 커브가 있을 수 있으나, 관계형 쿼리와 RLS의 보안 이점이 더 크다고 판단했다.

(2026-10 업데이트: 이 결정은 ADR-004에서 부분적으로 수정됨 — 커스텀 backend 추가)

### ADR-003: 아이 로그인은 QR 기기 연결 방식

**결정**: 아이 계정은 이메일/비밀번호 없이, 부모 폰에 표시된 QR을 아이 기기에서 스캔해 연결하는 방식으로 로그인한다.
**이유**: 만 7~12세 아이가 이메일/비밀번호를 직접 관리하기 어렵고, 개인정보(이메일 등)를 최소한으로 수집한다는 원칙에 부합한다.
**트레이드오프**: 기기 분실/변경 시 재연결 절차가 필요하며, QR 토큰은 일정 시간 후 만료시켜 탈취 위험을 줄인다.

### ADR-004: Supabase 단독 백엔드에서 커스텀 Node.js backend 추가로 전환

**결정**: ADR-002의 "Supabase만을 백엔드로 사용한다"는 결정을 수정한다. Express + TypeScript 기반 `backend/` 서버를 추가하고, 다음 세 가지 작업만 이 서버를 통해 처리한다.

1. 가족 생성 및 최초 보호자 멤버십 부트스트랩, 초대 코드 발급/redeem, 아이 추가(1:1 방+칭찬판 동반 생성)
2. 아이 QR 로그인 토큰 발급/교환 (디바이스 연결)
3. 푸시 알림 디스패치 (Supabase Database Webhook 수신 → Expo Push API 호출)

그 외 일상적인 데이터 읽기/쓰기(대화, 기분, 칭찬, 반응)는 ADR-002 원래 설계대로 frontend가 Supabase를 직접 호출하며 RLS로 보호된다.

**이유**: 가족 생성/초대/아이 추가/QR 로그인은 "멤버십 행이 아직 없는 상태에서 자기 자신을 만드는" 부트스트랩 문제거나, 여러 테이블(member+room+praise_board)을 한 트랜잭션으로 원자적으로 묶어야 하는 작업이라 RLS insert 정책만으로 안전하게 표현하기 어렵다. QR 로그인은 Supabase Auth Admin API(Service Role 전용)가 필요해 클라이언트에서 수행할 수 없다. 푸시 디스패치는 DB 변경을 감지해 외부 API(Expo)를 호출하는 상시 서버 로직이 필요하다. 반면 대화/기분/칭찬은 Supabase Realtime+RLS로 이미 충분히 안전하므로 전부 backend로 proxy하면 불필요한 지연과 복잡도만 늘어난다.

**트레이드오프**: 운영해야 할 서버가 하나 늘어난다(배포/모니터링 책임 증가). Service Role 키 사용 범위를 위 3가지로 한정하고, backend는 가능하면 사용자 JWT를 Supabase에 그대로 전달(passthrough)해 RLS가 계속 적용되게 한다. RLS는 모든 경로에서 defense-in-depth로 유지한다.
